# P11 slice 5 gate — Derived Baseline

1. **Replaces `SpendChangeParams.annualSpend`** (src/core/plan.ts:1056, entry `SPEND_CHANGE`, plan.ts:483). It is a household **annual level, in today's money**, raised monthly by `inflateStated(...cpi...)` (src/core/projection.ts:8623) then divided by 12 (`monthlySpendFromAnnual`, projection.ts:842-846) into `HOUSEHOLD_SPENDING_LINE` (projection.ts:1576). Doc at projection.ts:1576-1577 and TODO.md:8580-8581 state explicitly it is **NOT total outgoings**: mortgage repayment is **excluded** ("ADDITIONAL to the stated spending level", projection.ts:8569-8576; TODO.md:8581), `ONE_OFF_EXPENSE` is additional (projection.ts:1577, own line ONE_OFF_EXPENSE_LINE), and "every tax line" is additional (projection.ts:1577). Aged-care fees are separate named lines (AGED_CARE_* constants, projection.ts:1584-1591). Income tax and super contributions/insurance never touch `annualSpend` at all — they're computed household-income-side, not stated spend.

2. Fixed `CATEGORIES = ['Committed','Discretionary','One-off']` (src/core/ledger.ts:56) has **no transfer/exclusion marker**. Must exclude from any baseline: inter-account transfers (incl. credit-card repayment, offset/savings moves), mortgage repayments (modelled separately, double-counts with #1), inflows/refunds/income, investment purchases (wealth move, not spend). CONTEXT.md:277-278 calls the top level "fixed... because the projection depends on it" — that's a constraint on the *existing three*, not an explicit ban on a fourth. Smallest closing design: add a 4th fixed category, e.g. `'Excluded'` (or `'Transfer'`), never fed into the baseline sum, alongside a per-Categorisation Rule that can target it — cheaper than an exclusion flag since it reuses the existing Category/Categorisation/Rule machinery untouched. No doc forbids adding it; it does require touching `CATEGORIES`, `Category` type, and CONTEXT.md's term list.

3. Nothing in ledger.ts computes a baseline yet (not built — P11-7 unchecked). `reverses` (ledger.ts:85, LedgerReversalError) already cancels a reversed Transaction to the cent at the ledger level, so a correctly-reversed Transaction is already netted out before baseline code ever sees it. Positive amounts in a spending category (plain refunds, not `reverses`-linked) are not addressed anywhere. **Recommend: net them** (sum signed amounts per category, don't zero-floor) — the ledger is signed Cents (ledger.ts, "money OUT negative"), and netting is the only reading consistent with `reverses` already netting exact cancellations; excluding refunds entirely would overstate spend inconsistently with how reversals are already handled.

4. Not specified anywhere. **Recommend: include-and-name** — sum uncategorised outflows into the baseline (labelled "uncategorised" in the provenance breakdown, P11-11) rather than block-until-categorised or silently exclude. Per ADR-0004 (docs/adr/0004:19) and the project's standing "conservative direction" rule (projection.ts:1584, TODO.md:1855 "silently adding it would... make the forecast worse than the life" — i.e. the house style treats overstated spend as the safe-failure side), including uncategorised outflows overstates spend, which is the conservative error in a retirement forecaster (understating spend risks running out of money unseen). Excluding them understates spend — the dangerous direction. Blocking is the safest data-integrity option but conflicts with "never silently reclassify" (ADR-0004) forcing a stall; include-and-name is closest to the existing "offer, never bind" philosophy.

5. P11-9 text (TODO.md:8641) is one line: "Exclude One-off items from the recurring baseline; re-add as amortised lines." concept.md:272-274 gives the rationale (a roof shouldn't permanently inflate ongoing spend) but **no amortisation method is specified** — no window length, no straight-line-vs-other, no re-entry mechanism (a new `ONE_OFF_EXPENSE`? a synthetic recurring add-on?). **Not buildable as-is** — the exclusion half is trivial (filter `category === 'One-off'` out of the Committed/Discretionary sum), but "re-add as amortised" needs a user decision on method before code.

6. `inflateStated(cents, cpi, asAtDate, month)` (src/core/priceLevel.ts, exported) is the CPI lens; `priceLevelFactor` under it explicitly documents "A month BEFORE `asAtDate` gives a factor below 1... nothing here forbids one and a defined answer is better than a silently wrong one" (priceLevel.ts). So it already handles history: feed a past ledger month as `month` and `asAtDate` = today, and it correctly inflates (factor >1 since past < today in the (1+cpi)^((asAtDate−month)/12) sense — check sign: `monthsBetween(asAtDate, month)` is negative for past month, giving factor <1, which would *deflate*, not inflate). **Caller must invert the args**: to bring a past nominal amount UP to `asAtDate` money, call with `asAtDate=<past month>, month=<today>` effectively, i.e. `inflateStated(cents, cpi, historicalMonth, asAtDateToday)` — same function, function handles months on either side of its "asAtDate" argument fine, just requires the baseline code to pass the historical ledger month as the *base* argument and today as the *target*.

**Decisions needing the user (max 4):**
- **Fixed-category gap (#2):** add a 4th category (Excluded/Transfer) so transfers/mortgage/income/investment moves can be marked and never summed. Recommend: yes, minimal addition, reuses existing Categorisation/Rule machinery.
- **Uncategorised outflows (#4):** include-and-name vs. block. Recommend: include-and-name (conservative, avoids ADR-0004 stall).
- **Refunds (#3):** net vs. exclude. Recommend: net (consistent with `reverses` already netting).
- **One-off amortisation method (#5):** no spec exists (window length, re-add mechanism). Recommend: straight-line over a user-chosen window (default 5y), re-added as a synthetic recurring `SPEND_CHANGE` delta or a note — needs explicit user ruling before build.

**Verdict: GO-after-decisions.** Core CPI mechanism (#6) and the annualSpend target semantics (#1) are solid and buildable now; the four items above are genuine open decisions, not implementation detail, and P11-9 in particular has no buildable spec yet.

## Rulings, 2026-09-28

- **User:** a fourth fixed category, labelled **"Other"**, marks not-spending: transfers between own accounts, card repayments, mortgage payments, income and investment purchases. The picker says "Other (not spending: left out of the spending figure)", and the offer shows the Other total separately (LIZ, to guard against misfiled real purchases).
- **User:** one-offs are excluded and their 12-month total is shown beside the offer. Nothing is amortised automatically; the user adds ONE_OFF_EXPENSE entries if they want them.
- **LIZ, by precedent:** refunds net against spending (as reversals do). Uncategorised outflows are INCLUDED and named (the conservative failure mode). Accept appends a SPEND_CHANGE dated asAtDate through the normal entry-save path, and later dated SPEND_CHANGEs stand (P10: never flatten a phased plan). One figure is offered, with Committed/Discretionary shown as a breakdown.

## Superseded, 2026-09-28 (user-reported defect)

The window above ("12 whole calendar months before asAtDate") and LIZ's ×12/months scaling were both wrong. On the user's first import (34 rows, 30 Aug–28 Sep, asAtDate 25 Sep) they gave $240/yr. The window is now the data's own dates: it ends on the latest transaction and reaches back at most 365 days. Under a year it is scaled by 365/days, and under 28 days there is no offer.
