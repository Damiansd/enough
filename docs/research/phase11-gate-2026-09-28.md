## 2. Gaps — concrete decisions blocking a first slice

1. **CSV column-mapping persistence.** Docs say "CSV import with column mapping" but never say
   whether a mapping is remembered per bank/file-shape or re-entered every import.
   Recommend: key a saved mapping by the CSV header row (exact column names, order-independent);
   re-prompt only when headers don't match a saved mapping. Why: matches ADR-0004's "saved rule"
   precedent (rules persist, apply next time) and needs no bank-specific code.

2. **Duplicate rows on re-import** (a household re-exports and re-imports an overlapping date
   range). Not mentioned anywhere. Recommend: dedupe on exact match of (date, amount, raw
   description) before append, silently — this is hygiene on the append step, not a "derived
   value," so it doesn't trip ADR-0004's offer-don't-bind rule. Why: without this the ledger is
   append-only + it becomes trivially double-counted on the very first overlapping re-import.

3. **Rule-match granularity in bulk review** (P11-6: "suggest; bulk review before commit").
   Ambiguous whether the user accepts/rejects the whole rule-batch ("47 → Groceries, accept?") or
   can uncheck individual transactions within it. Recommend: whole-batch accept/reject for slice
   1, individual override deferred — matches the P15-11 precedent's actual granularity (call-level,
   not line-level) and ADR-0004's own example is phrased as one yes/no.

4. **Baseline recompute trigger.** Not stated whether the Derived Baseline re-offers itself
   automatically as new months of transactions arrive, or only on manual request. Recommend:
   manual "recompute" action only, offered result never auto-replaces an already-accepted
   Setting — matches ADR-0004's "the Setting only changes when accepted" (docs/adr/0004:13-14)
   read literally.

5. **Inflation index/rate source** for "inflate history to today's money" (TODO.md:8627,
   concept.md:275-277). No index is named anywhere in concept.md, CONTEXT.md, or the ADRs.
   Recommend: reuse whatever CPI/indexation figure the projection engine already uses for other
   inflation adjustments (check src/core for an existing CPI constant before inventing a second
   one) — needs a codebase check, flagged rather than answered here since it's a "does one
   already exist" question, not a genuine unknown.

These five are the ones that block a first vertical slice. Everything else in P11-1..11 (file
separation, fixed categories, provenance display, offer-not-bind) is already fully pinned by
ADR-0004 + CONTEXT.md and needs no user decision.

## 3. Proposed slice order

1. **Ledger core type + append-only guard, no UI.** `Transaction`, `Category` (fixed top level +
   user subcategory string), `Ledger` type in src/core, mirroring the
   `requireAConformingLedger`/`appended` pattern already proven in transferBalanceAccount.ts, with
   read/write through `/api/ledger` (already live). Must fail if: appending an entry with a day
   before the ledger's last entry, or removing/mutating an existing entry, is accepted without
   throwing. No user decision needed — pure port of an existing pattern to a new shape.

2. **Manual entry UI (no CSV yet).** One transaction at a time into the ledger via the core type
   from slice 1. Must fail if: a manually entered Transaction can be edited or deleted in place
   after being saved (only append is allowed).

3. **CSV import + column mapping** (needs decision #1). Parse arbitrary CSV, map columns to
   date/amount/description once per header-shape, append parsed rows through the slice-1 guard.
   Must fail if: importing the same file twice produces duplicate ledger entries (needs decision
   #2), or an unmapped/malformed row is silently dropped instead of surfaced.

4. **Categorisation rules — suggest + bulk review** (needs decision #3). Rule = description
   substring → Category/subcategory; matching transactions previewed before commit. Must fail if:
   accepting a rule changes categories on transactions that were already manually categorised, or
   a rule silently reapplies without the review screen on a later import.

5. **Derived Baseline calculation + offer screen** (needs decisions #4, #5). Trailing 12 months,
   One-off excluded and shown as separate amortised line, inflated to today's dollars, with
   provenance (transaction list, window, rule set) displayed. Must fail if: the computed baseline
   ever writes to the spending Setting without an explicit accept click, or the figure shown
   omits which transactions/window fed it.

6. **Provenance drill-down on an already-accepted baseline** (polish/traceability). Must fail if:
   after acceptance, there is no way to see which transactions produced the accepted number.

## 4. Contradictions / friction with current architecture

- None found that block Phase 11 outright. The ADR-0008-style concern named in the prompt (plan
  served from disk vs. browser storage) doesn't arise here — the ledger already follows the exact
  same disk-file-served-by-a-dumb-server pattern as the plan (server/index.mjs:13).
- One thing worth flagging as friction rather than contradiction: `/api/ledger`'s PUT is a
  whole-file overwrite (server/index.mjs:25-33), identical to `/api/plan`. That's consistent with
  ADR-0007/0008's "server holds no state" stance, but it means append-only-ness is purely a
  client-side (src/core) invariant with nothing stopping a buggy client from PUTting a truncated
  or edited ledger. This is exactly the same trust model plan.json already lives with for Journal
  Entries, so it's not a new problem — just worth the same vigilance P3-41/plan.ts already
  applies (private-member witness pattern), which slice 1 should reuse rather than re-derive.
- P15-11's own TODO line calls itself "same review surface as P11-6," but its actual granularity
  (whole-proposal accept/reject, not line-level) doesn't match the literal "bulk review" language
  of P11-6/ADR-0004's "47 transactions... accept?" example closely enough to be reused as-is — see
  decision #3. Not a contradiction in the docs, just a claim in a checked-off TODO item that's
  aspirational rather than actually shared code yet.

## Verdict

**GO after decisions** — slice 1 (ledger core type + append-only guard) can start today with zero
user input; slices 3-5 need decisions #1-#5 above before they can be built without guessing.
